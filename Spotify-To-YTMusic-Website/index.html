Spotify-To-YTMusic

This fork walks a music library across the road: out of Spotify as a backup file, order fixed, signed in at the far kerb, then liked songs, liked albums, and playlists carried over one search at a time. The guard decides, track by track, what may go over and what stays behind after its retries run out.

Open the repo The crossing itself

1

Get the list out of Spotify Stage one, the near kerb

The tool does not talk to Spotify directly. It works from a file called playlists.json produced by the separate spotify-backup.py script, which the user runs after authorising access to their Spotify account, typically with these arguments:

python3 spotify-backup.py playlists.json --dump=liked,playlists --format=json

In this fork the backup script argument parsing was fixed: its documented --dump and --format arguments were previously ignored, and bad values are now refused.

2

Fix the order Stage two, turning the file round

reverse_playlist.py reads that JSON file and reverses each playlist, because the backup lists tracks in an order the author did not want carried over. It writes a backup of the original file first.

In this fork it also checks its input: a file that is not valid JSON, or that has no playlists list, gets one error line and is left alone instead of producing a traceback.

python3 ./reverse_playlist.py ./playlists.json -r
3

Sign in to the destination Stage three, the far kerb

YouTube Music access runs through ytmusicapi oauth, which writes oauth.json. Without that file the backend stops with an error message telling the user to log in.

ytmusicapi oauth

Guard note: oauth.json holds a live session token. Keep it private while the app is authorised.

4

The crossing itself Stage four, the real command names, set as a kerbside list

  • load_liked likes the Spotify liked songs on YouTube Music.
  • load_liked_albums brings liked albums across as liked songs.
  • list_playlists shows what exists on both sides.
  • copy_playlist moves one named playlist.
  • copy_all_playlists moves every playlist while pointedly leaving the Liked playlist out.
  • create_playlist makes a destination list.
  • gui opens the tabbed graphical window.

Matching works like this: the code searches YouTube Music for the album by the same artist, checks the first three album results for a track with the exact same name, then falls back to a song search. Algorithm 0 takes the first song result. Algorithm 1 demands an exact match on track, artist, and album. Algorithm 2 tries a fuzzy match with bracketed text stripped, then searches videos.

A track can therefore be matched wrongly, especially under algorithm 0. A track with no acceptable match raises an error and, in this fork, is skipped after three retries rather than retried for ever. Other lookup failures allow ten attempts, and a failed playlist addition allows ten attempts with a doubling wait capped at 320 seconds before that track counts as an error and the copy moves on. Copying a playlist whose name already exists on YouTube Music reuses that playlist in this fork instead of always creating another one. Re-running a copy is described in the upstream notes as safe against duplicates.

Guard note: an unmatched track is skipped after three retries. The guard keeps a count of who did not cross.

5

Cautions at the far kerb Stage five, read before the traffic moves

Run with --track-sleep=3 to slow the rate and lower the risk of a ban. Expect long runs on big libraries. Use a desktop operating system, because the tool does not run on mobile.

Know the limits: no playlists.json means no transfer, no oauth.json means no destination, obscure titles may match badly or not at all, and liked songs need their own command because copy_all_playlists skips them.

Guard note: copy_all_playlists leaves liked songs behind. Run load_liked for them.

The fork is covered by 17 tests with mocked YouTube Music objects, no account needed: python3 -m unittest discover -s tests. Background and upstream detail live in the repo README.
